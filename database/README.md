# База данных

PostgreSQL 16+, схема из 13 таблиц в 3НФ, multi-tenant: каждый склад изолирован составными внешними ключами (подробности — в шапке `01_schema.sql`).

## Как поднять локально

```bash
createdb warehouse_db
psql -d warehouse_db -f 01_schema.sql
psql -d warehouse_db -f 02_seed.sql
```

Пересоздать с нуля:

```bash
dropdb warehouse_db
createdb warehouse_db
psql -d warehouse_db -f 01_schema.sql -f 02_seed.sql
```

## Windows: одним файлом

Двойной клик по `setup_windows.bat` (или запуск из `cmd`). Он сам найдёт `psql.exe`,
спросит пользователя и пароль PostgreSQL, пересоздаст базу `warehouse_db` и загрузит
`01_schema.sql` + `02_seed.sql`. В конце напечатает строку подключения для бэкенда.

База обязательно создаётся в **UTF-8**: в сиде есть символы `×` и `−`, которых нет в
Windows-1251, а на русской Windows Postgres по умолчанию создаёт базы именно в ней —
обычные `createdb` + `psql -f` там падают на 61-й строке `02_seed.sql`.

Без `psql` (только pgAdmin): создать базу `warehouse_db` с кодировкой **UTF8** и выполнить
в Query Tool сначала `01_schema.sql`, потом `02_seed.sql`.

Рабочие логины (пароль `password123`): `a.kovalev` и `v.orlova` — директора складов 1 и 2,
`admin` — администратор. У остальных пользователей в сиде заглушки вместо хэшей — войти
ими нельзя.

## Строка подключения для backend (appsettings.json / .env)

```
Host=localhost;Port=5432;Database=warehouse_db;Username=<твой mac username>;Password=
```

Локальный Postgres через Homebrew на macOS по умолчанию работает без пароля (`trust`-аутентификация для локальных подключений) — если бэк не может подключиться, проверь `pg_hba.conf` (`brew info postgresql@16` покажет путь).

## Файлы

- `01_schema.sql` — DDL: таблицы, PK/FK, CHECK-констрейнты, индексы.
- `02_seed.sql` — тестовые данные (номенклатура и контрагенты взяты из UI-мокапов).
- `setup_windows.bat` — установка одним файлом на Windows (см. выше).

## Что хранится в БД, а что нет

Принцип: всё, что можно назвать данными, отдаёт API из БД; фронт ничего не зашивает.

| Таблица | Зачем |
| --- | --- |
| `units` | единицы измерения (`шт`, `рул`…); товар ссылается на неё через `products.unit_id` |
| `document_types` | не только название: `prefix` и `number_width` (формат номера), `counterparty_type_id` (какого контрагента можно указать, `NULL` — никакого), `has_prices`, `stock_effect` |
| `document_number_counters` | по строке на пару «склад + тип документа» — откуда API берёт следующий номер |
| `warehouses.time_zone` | часовой пояс склада: по нему определяется календарный день документа |
| `users.password_changed_at`, `must_change_password`, `last_login_at` | основа для смены пароля и профиля |

`stock_effect` — единственное поле, из которого выводится поведение типа при проведении:
`increase` (приход, остаток растёт), `decrease` (расход, нельзя уйти ниже нуля), `adjust`
(инвентаризация, количество — знаковая дельта). Сравнивать название типа строкой в коде не нужно.

В БД **нет**: текстов статусов остатка («Норма», «Ниже минимума»), прав ролей, меню — это
правила, они в C#.

### Нумерация документов

Номер выдаёт только API, одним атомарным запросом (блокирует строку счётчика, поэтому два
параллельных документа не получат один номер; выполнять в одной транзакции со вставкой
документа — тогда при ошибке откатится и счётчик, и дырок не будет):

```sql
INSERT INTO document_number_counters (warehouse_id, type_id, last_number)
VALUES (@warehouse, @type, 1)
ON CONFLICT (warehouse_id, type_id)
DO UPDATE SET last_number = document_number_counters.last_number + 1
RETURNING last_number;
```

Номер = `prefix` + `-` + `last_number`, дополненный нулями слева до `number_width`
(`ПР-004414`, `ЗК-88107`, `ИН-0043`). Номер уникален в рамках склада, не глобально.

### Что убрано

Тип документа «Перемещение» (при изоляции складов перемещать нечего) вместе с
`documents.target_warehouse_id`, и текстовое `documents.status` («Разгрузка», «Собран» —
нигде не показывалось и с остатками не связано; состояние документа — это `is_posted`).

## Важное решение, которое нужно знать при написании бэка

Таблица `stock` — это кэш текущих остатков, а не источник истины. Она **не редактируется напрямую** — только через проведение документов (`documents` / `document_items`, эндпоинт `POST /api/documents/{id}/post`). Проведение — одна транзакция (один `SaveChanges()` уже атомарен), иначе при параллельном проведении двух расходных документов остаток может уйти в минус мимо `CHECK (quantity >= 0)`.
